# 📋 Engenharia de Requisitos (ER)

> *"A parte mais difícil de construir um sistema de software é decidir exatamente o que construir."*  
> — **Fred Brooks**

---

## ⚡ O que é ER?

A **Engenharia de Requisitos** é o processo de descobrir, analisar, documentar e gerenciar o que um software deve fazer e quais restrições
ele deve respeitar.

**Objetivo Principal:** Garantir que a equipe desenvolva a **coisa certa**, reduzindo retrabalho e custos futuros.

---

## 🎯 Objetivos Principais

* 🤝 **Alinhamento:** Colocar clientes e desenvolvedores na mesma página.
* 💰 **Economia:** Corrigir falhas no início do projeto custa até 100x menos do que no final.
* 💡 **Valor:** Garantir que o produto resolva o problema real do negócio.
* 🧪 **Base para Testes:** Servir de guia para verificar se o sistema funciona corretamente.

---

## 💡 Tipos de Requisitos

| Categoria | O que representa? | Exemplo Prático |
| :--- | :--- | :--- |
| **Funcional (RF)** | O que o sistema faz (funcionalidades). | *"Permitir pagamento via PIX."* |
| **Não-Funcional (RNF)** | Como o sistema deve ser (desempenho, segurança, usabilidade). | *"O pagamento deve ser processado em até 
segundos."* |
| **Regra de Negócio (RN)** | Regras e políticas da organização. | *"Desconto de 15% apenas para clientes VIP."* |

---

## 🔄 Ciclo de Vida da ER

A ER não acontece uma única vez, é um processo contínuo e iterativo:

> 🔍 **Elicitação** ➔ 🤝 **Análise** ➔ 📝 **Especificação** ➔ ✅ **Validação** ➔ 🔄 **Gestão Contínua**

* 🔍 **Elicitação & Descoberta:** Coletar necessidades com os envolvidos.
* 🤝 **Análise & Negociação:** Priorizar o que é viável e resolver conflitos.
* 📝 **Especificação:** Documentar (Histórias de Usuário, Casos de Uso, Telas).
* ✅ **Validação:** Confirmar com o cliente se a documentação está correta.
* 🔄 **Gestão:** Acompanhar mudanças de escopo e rastrear impacto ao longo do projeto.

---

## 🛠️ Técnicas & Ferramentas Comuns

### Como descobrir requisitos?
* 💬 **Entrevistas e Questionários:** Conversas diretas ou formulários com usuários.
* 👥 **Workshops (JAD):** Reuniões intensivas com a equipe e o cliente.
* 👁️ **Observação:** Acompanhar o trabalho real do usuário no dia a dia.
* 🎨 **Prototipagem:** Criar telas simples para validar ideias antes de codificar.

### Como documentar?
* 📖 **User Stories (Histórias de Usuário):**  
  *Exemplo:* *"Como [cliente], eu quero [pagar via PIX] para que [a compra seja aprovada na hora]."*
* 📐 **Casos de Uso & Diagramas UML:** Para detalhar fluxos técnicos e interações.

---

## ✅ Boas Práticas (Critério INVEST)

Para criar boas *User Stories*, utilize a sigla **INVEST**:

| Letra | Conceito | Significado |
| :---: | :--- | :--- |
| **I** | **Independente** | Pode ser desenvolvida sem depender de outra. |
| **N** | **Negociável** | Detalhes podem ser ajustados com o time. |
| **V** | **Valiosa** | Entrega valor real para o usuário/negócio. |
| **E** | **Estimável** | A equipe consegue prever o tempo/esforço necessário. |
| **S** | **Small (Pequena)** | Cabe dentro de um ciclo curto (Sprint). |
| **T** | **Testável** | Possui critérios claros de aceite. |

---

## ⚠️ Cuidados e Desafios

* ❌ **Ambiguidade:** Requisitos confusos geram interpretações erradas.
* 📈 **Scope Creep (Aumento de Escopo):** Adicionar novos recursos sem reajustar prazos e custos.
* 🗣️ **Falha de Comunicação:** Linguagem técnica demais que o cliente não entende.
